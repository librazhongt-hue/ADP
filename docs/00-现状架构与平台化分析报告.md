# Autonomous Decision Platform（ADP）现状架构与平台化分析报告

> 状态：仅分析，未修改任何现有代码。
> 参考实现（Reference Implementation）：日本陆上养殖项目（Japan Aquaculture）
> 分析范围：`/home/gmm/srv` 下全部相关仓库
> 日期：2026-07-09

---

## 0. 结论先行（TL;DR）

1. `/home/gmm/srv` 下实际是 **6 个独立仓库 + 1 个 MQTT 配置**，共同组成"日本陆上养殖"这一个业务系统，而不是一个 monorepo。它们之间通过 **HTTP / WebSocket / MQTT / 共享 MySQL / 消息队列** 松耦合。
2. 系统里已经**天然存在**一条 Sense→Understand→Decide→Act→Observe→Learn 的雏形闭环，但它是**隐式的、分散在 3～4 个进程里的**，没有被抽象为统一的框架。这正是 ADP 要做的事：把这条隐式闭环**显式化、通用化、可配置化**。
3. 当前代码中"通用能力"和"养殖业务"几乎处处混在一起（同一个文件里，通用的 LLM 调用框架和"南美白对虾"的提示词写在一起）。平台化的核心工作量不是"抄代码"，而是**做分离手术**：把 Prompt / 阈值 / 表结构 / 工具定义 中的业务参数全部外置为配置或插件。
4. 建议 ADP 的边界按**六层管道 + 插件化能力**来划分，而不是按"现有目录名"来划分——因为现有目录（agent / agent_new / backend / deviceagent / cognitive-center）职责本身有交叠和历史债务，直接照搬会把债务一起搬进平台。

## 1. 现状总览：这是一个由 6 个仓库构成的分布式系统

| 仓库 | 角色 | 端口 | 关键技术 |
|---|---|---|---|
| `ai_japan` | 现场采集/控制客户端（Edge） | 内部心跳 ws://:8001 | Python 调度器 |
| `japan-aquaculture-project/backend` | 业务主服务：数据、任务、调度、AI喂食决策、MQTT | Flask :5002 | Flask + APScheduler + paho-mqtt |
| `japan-aquaculture-project/agent`（旧） | 对话 Agent v1（含 LangGraph 数据摄入管线） | FastAPI（未知端口，历史版） | FastAPI + LangGraph + LangChain |
| `japan-aquaculture-project/agent_new`（新） | 对话 Agent v2（意图路由+多分支Handler） | FastAPI :8000 | FastAPI（无 LangGraph 运行时） |
| `deviceagent` | 设备执行子 Agent（Act 层） | FastAPI :5004 | LangGraph + LangChain ReAct Agent |
| `cognitive-center` | 认知/决策后台处理（消息队列驱动） | 无 HTTP，continuous 进程 | LangGraph + 自研 Orchestrator |
| `japan_shrimp_detect` | YOLO 虾体检测服务 | FastAPI :5005 | Ultralytics YOLO |
| `mosquitto` | MQTT Broker 配置 | :1883 | 仅配置，被 backend 代理使用 |

耦合方式：

```
ai_japan ──HTTP/WS──▶ backend(:5002) ──MQTT(:1883)──▶ mosquitto ──▶ 硬件(水泵/鼓风机等)
                         │  ▲
                         │  └── 反向：deviceagent 回传投喂记录 / MAC 状态
                         │
                         ├──HTTP──▶ japan_shrimp_detect(:5005) [YOLO检测]
                         │
                         ├──共享MySQL──▶ cognitive-center(continuous 消费 message_queue)
                         │
                         └──HTTP(审批后触发)──▶ deviceagent(:5004) ──LangGraph──▶ 喂食机/MAC硬件

用户 ──HTTP/WS──▶ agent_new(:8000) ──意图路由──▶ ┬─ 专家RAG服务(:5003, 未探索)
                                                 ├─ deviceagent(:5004) [设备控制类对话]
                                                 └─ backend 数据(只读咨询)
```

**关键判断**：这不是"一个系统的内部模块"，而是**已经在事实上运行着的分布式多智能体系统**——只是每个"智能体"的边界是历史演化出来的，不是设计出来的。这对 ADP 是好消息：说明"多进程协作"这个形态本身不需要推翻，需要推翻的是"边界画得不合理、能力封装得不干净"。

## 4. 六阶段闭环在现状系统中的映射

下表把系统里已经存在、但分散在不同进程的六阶段能力对齐到 Sense/Understand/Decide/Act/Observe/Learn，作为 ADP 抽象的基础蓝图。

| 阶段 | 现状实现（最成熟的一条链路：backend AI 喂食决策） | 现状实现（对话链路：agent_new） | 现状问题 |
|---|---|---|---|
| **Sense** 感知 | `build_pond_context()` 聚合传感器/虾况/喂食记录/日志 | 用户消息 + 并行联网搜索 + 天气 + 附件 | 感知源是硬编码列表，非插件化 |
| **Understand** 理解 | 上下文JSON组装 + 确定性投喂率计算 | 意图识别 `recognize_intent()` | 两条链路的"理解"实现方式完全不同，无共同抽象 |
| **Decide** 决策 | LangChain `ChatOpenAI` 生成任务 JSON | if-else 分支路由到专家/设备/闲聊 | 决策没有统一的"决策引擎"接口，一个用LLM直出JSON，一个用规则路由 |
| **Act** 执行 | 写 `work_tasks` → 审批 → HTTP 触发 deviceagent | HTTP 转发 deviceagent / 专家RAG | Act 层相对统一（都走 deviceagent），这是现状中**最接近平台化**的一层 |
| **Observe** 观察 | `DecisionRecordingService` 记录运行结果、置信度 | 保存对话历史 | 观察数据结构不统一，喂食决策有结构化记录，对话只有日志 |
| **Learn** 学习 | `parse_and_clamp_next_decision` 调整下次决策时机 | 无（仅历史作为下轮 context） | **全系统最薄弱的一环**：没有反馈回路把 Observe 的结果系统性地喂回 Decide/Understand，只有"下次何时决策"这个单一学习信号 |

**结论**：Act 层（对接 deviceagent）和 Observe 层的雏形（decision_recording）是现状中**信号最强、最值得直接抽象**的两层；Learn 层几乎是空白，ADP 需要**从零设计**，不是从现状"提取"。

## 5. 迁移建议：哪些迁移到 ADP，哪些留在 Aquaculture

### 5.1 建议迁移到 ADP（平台层）

以"能力模式"而非"具体文件"描述（因为现状代码大多混杂业务参数，迁移时应是**重新设计接口、参考现状实现**，而不是整体搬运文件）：

| ADP 能力模块 | 参考现状实现 | 迁移方式建议 |
|---|---|---|
| **LLM Gateway**（统一模型调用/切换/重试/流式） | `agent_new/core/llm.py`, `deviceagent/llms/llm_manager.py` | 抽取接口，业务侧只传 model/prompt/tools |
| **Prompt Registry**（外部化、多源加载、版本化） | `agent_new/prompts/__init__.py`, `cognitive_model/config/prompt_manager.py` | 保留"文件/DB双源"设计，去除养殖专属默认值 |
| **决策图引擎**（StateGraph 编排、条件路由、Command跳转） | `deviceagent/graph/builder.py`, `agent/graph.py` | 抽象为"节点=感知/理解/决策/执行插件"的通用 Graph Runner |
| **工具调用框架**（工具注册、ReAct执行、权限/超时控制） | `deviceagent/tools/tool_provider.py`, `cognitive_model/tools/tool_registry.py` | 统一为 Tool SDK，业务侧只需实现工具函数并注册 |
| **意图识别/路由框架** | `agent_new/core/intent.py` | 保留"关键词预检+LLM兜底"两级模式，业务侧配置意图类别 |
| **记忆管理**（短期会话 + 长期主题记忆） | `cognitive_model/hippocampus/*` | 这是全系统里**设计最完整的可复用组件**，优先迁移 |
| **任务调度**（once/daily + DB持久化 + 恢复） | `deviceagent/scheduler/task_scheduler.py`, `backend/services/shared_scheduler_service.py` | 三个仓库各写了一套，迁移时应**收敛为一套** |
| **决策记录/可观测性**（运行追踪、成功/失败、下次触发时间） | `backend/services/decision_recording_service.py` | 这是 Observe/Learn 阶段最具复用价值的组件，需泛化"风险等级→间隔"为可插拔策略 |
| **Act 执行网关**（统一的"外部Agent/设备"调用协议：HTTP+SSE） | `agent_new/services/device_expert_service.py`, `backend/services/work_task_service.py` 的调用部分 | 统一为 ExecutorClient 接口，具体设备协议作为插件 |
| **会话/状态管理** | `agent*/services/session_service.py`, `cognitive_model/handlers/session_state_manager.py` | 通用会话生命周期 + 多轮确认状态机 |
| **配置管理范式** | 各仓库的 Settings 模式 | 统一为 ADP 的分层配置（platform defaults + project overrides） |
| **WebSocket/流式通信协议** | `agent_new/websocket/handler.py` | 抽象为通用的 init/heartbeat/stream 协议层 |

### 5.2 建议继续保留在 Aquaculture（参考实现层）

| 保留内容 | 原因 |
|---|---|
| 池塘/批次/虾况/传感器/喂食机等**领域数据模型** | 与养殖业务强绑定，是"数据"不是"能力" |
| **投喂率计算算法**（`feeding_rate_service.py`） | 领域专有算法，不同养殖品种/项目差异巨大 |
| **喂食机、MAC设备、YOLO检测**等具体硬件/算法适配 | 硬件协议、模型权重是本项目专属资产 |
| 养殖相关**Prompt 内容**（话术、专家知识） | 内容属于领域知识库，通过 Prompt Registry 挂载即可，不需要改变宿主代码 |
| 告警阈值（DO/pH/氨氮等） | 领域经验值，应作为该参考实现的配置，而非平台代码 |
| `ai_japan` 现场采集客户端 | 是"Sense 阶段的一种具体传感器接入实现"，属于参考实现的感知插件 |
| `japan_shrimp_detect` YOLO 服务 | 是"Sense 阶段的一种具体算法感知源"，同样是插件而非平台核心 |

### 5.3 需要重写、不建议直接搬运的部分

| 内容 | 问题 |
|---|---|
| `cognitive_model/handlers/query_handler.py` 中 `_force_japan_aquaculture_decision()` | 业务名称硬编码进通用 Handler，需重新设计为"默认专家"可配置项 |
| `agent` 旧版的 LangGraph 数据摄入管线（`agent/graph.py`） | 与聊天路径脱节、未被实际使用，属于技术债，不应作为平台设计参考 |

## 6. ADP 平台边界（Boundary）定义

### 6.1 边界原则

> **ADP 只负责"闭环怎么转"，不负责"闭环里装的是什么"。**

具体来说：

- ADP 提供 **六个阶段的抽象接口 + 一个把它们串起来的运行时（Graph Runner / Loop Engine）**。
- 每个阶段的**具体实现是插件**，由接入项目（如 Aquaculture）提供，通过配置/注册的方式挂载，不侵入平台代码。
- ADP 提供跨阶段的**横切能力**：LLM Gateway、Prompt Registry、记忆、调度、可观测性、配置管理、通信协议。这些横切能力本身不含任何业务语义。
- ADP **不管理业务数据模型**（池塘、传感器、批次等 ORM/表结构均属于接入项目）。
- ADP **不直接对接具体硬件/设备协议**；ADP 定义"Executor 接口"，具体设备驱动（喂食机、MAC、摄像头）由接入项目实现。

### 6.2 边界表（一句话判断法）

| 问题 | 属于 ADP | 属于 Aquaculture（业务插件） |
|---|---|---|
| 这是"如何调用LLM"的机制吗？ | ✅ | |
| 这是"喂给LLM什么Prompt内容"吗？ | | ✅ |
| 这是"如何编排一个多步决策流程"的引擎吗？ | ✅ | |
| 这是"具体决策流程里有哪几步、每步做什么"吗？ | | ✅（通过插件注册到引擎） |
| 这是"如何记录一次决策的运行状态"的框架吗？ | ✅ | |
| 这是"喂食风险等级对应几分钟后再决策"这个具体数值吗？ | | ✅ |
| 这是"如何调用一个外部Agent/设备执行动作"的协议吗？ | ✅ | |
| 这是"喂食机每份=17g、MAC设备分类"这类具体协议细节吗？ | | ✅ |
| 这是"如何存取会话记忆"的机制吗？ | ✅ | |
| 这是"南美白对虾"、"池塘"、"死虾"这类领域词汇吗？ | | ✅ |

### 6.3 ADP 六阶段接口边界（形态草图，非最终API设计）

```
ADP.Sense      : 接收/拉取原始信号 → 统一 SenseEvent（来源、时间、payload）
ADP.Understand : SenseEvent(s) → 结构化 Context（意图、实体、置信度）
ADP.Decide     : Context → Decision（动作类型、参数、置信度、依据）
ADP.Act        : Decision → 调用 Executor（同步/异步/需审批）→ ActResult
ADP.Observe    : ActResult + 环境反馈 → 结构化 ObservationRecord
ADP.Learn      : ObservationRecord(s) → 更新策略/记忆/下次触发时机

Loop Engine    : 按项目配置的图结构，把以上阶段串成一个可运行、可中断、可重试的循环
```

接入项目（Aquaculture）只需要：
1. 实现若干 Sense 适配器（传感器HTTP接收、YOLO结果接收、日志导入…）
2. 实现若干 Understand 插件（意图识别的类别与规则、领域实体抽取…）
3. 提供 Decide 阶段用的 Prompt/规则/算法（喂食率计算、任务生成Prompt…）
4. 实现 Executor（deviceagent 客户端、MQTT客户端…）
5. 定义 Observe 的业务字段（决策记录里要存哪些养殖专属字段）
6. 定义 Learn 的策略参数（风险等级→间隔的具体数值表）

平台代码本身不出现"虾/池塘/喂食机"字样。

## 7. 对现状"三套并行决策路径"的平台化启示

现状中有三条相对独立的决策/编排实现：

1. `deviceagent`（LangGraph，Act为主，门禁+路由+执行）
2. `agent_new`（自研if-else路由，Understand+Decide为主）
3. `cognitive-center/cognitive_graph`（LangGraph，消息队列驱动的analyzer→decision→executor）

三者图结构模式高度相似（**门禁/预检 → 路由 → 分支执行 → 整合**），但各自独立实现，无共享抽象。这是平台化的**最强证据**：三次独立实现同一种模式，说明这个模式本身值得沉淀为 ADP 的 Loop Engine，而不是让第四个项目再写第四遍。
