## 专题讨论 1：通用调度器（`adp/scheduling`）设计范围

现状三个仓库各写了一套调度器（`ai_japan/src/scheduler`、`deviceagent/scheduler/task_scheduler.py`、`backend/services/shared_scheduler_service.py`），`docs/05` 已把职责拆成两层：

- `adp/scheduling`：底层定时器原语（"N分钟后执行一次"、"每天固定时间执行"），不知道"决策""Loop"概念。
- `adp/observability`：`list_pending_triggers` 提供"决策到期查询"的语义层。

需要讨论确认的点：

1. **调度器的执行模型**：进程内后台线程/asyncio 任务轮询（现状 `deviceagent` 是线程池），还是纯"提供 API，由外部 cron/K8s CronJob 定期调用"？两者对平台复杂度影响很大。
2. **调度器是否需要持久化**：现状 `deviceagent` 重启后从 DB `load_pending_tasks()` 恢复任务；平台版是否也需要"任务持久化+重启恢复"，还是只做内存态的定时器，持久化恢复完全交给 `observability` 的 `list_pending_triggers`（即调度器只负责"轮询到期"，不负责"记住有哪些任务"）？
3. **谁来"触发 Loop 运行"**：调度器扫描到期后，直接调用 `LoopEngine.start(...)`，还是只是发出一个事件/回调，由接入方决定何时真正触发？

## 专题讨论 2：分层配置（`adp/config`）设计范围

需要讨论确认的点：

1. **管什么**：至少包括——数据库连接串（供 A2 的 SQL Adapter 使用）、LLM Provider 的 API Key/Base URL、平台默认值（如 `FixedIntervalTriggerPolicy` 的默认间隔）。是否也要管"项目自定义的业务配置"（如喂食阈值），还是那部分完全交给参考实现自己的配置系统？
2. **分层方式**：现状每个仓库都是"Pydantic Settings + `.env`"模式。平台版是否延续这个模式（`pydantic-settings` 作为新增依赖），还是自己写一个更轻量的分层合并（platform defaults → project `.env` → 运行时覆盖）？
3. **与 SQL Adapter 的耦合**：`adp/config` 大概率要先做，因为 SQL Adapter 需要从某处读取数据库连接信息——这决定了本轮的实现顺序应该是 **先 config，再 SQL Adapter，再 scheduling**（scheduling 相对独立，可以最后做或并行）。

### 专题讨论1结论：通用调度器（`adp/scheduling`）

1. **执行模型**：进程内 `asyncio` 定时任务（与平台其余部分技术栈一致），不做线程池、不依赖外部 cron。
2. **持久化**：调度器**不自己持久化任务列表**。它只负责"按固定频率轮询"，到期任务的来源完全交给 `adp.observability` 的 `DecisionRecorder.list_pending_triggers(now)`；调度器重启后无需恢复"任务列表"，因为它本来就没有状态——下一次轮询会重新从 `list_pending_triggers` 查到所有到期项。
3. **触发方式**：调度器扫描到期记录后，调用一个注册的回调（`Callable[[DecisionRun], Awaitable[None]]`），由接入方决定回调里具体怎么重建 `LoopSpec` 并调用 `LoopEngine.start()`——调度器本身不知道 `LoopSpec`/`LoopEngine`。

### 专题讨论2结论：分层配置（`adp/config`）

1. **管什么**：平台基础设施配置（数据库连接、LLM Provider 密钥/BaseURL、调度器轮询间隔等平台默认值）。
2. **业务扩展机制**：`PlatformSettings`（`pydantic-settings` 的 `BaseSettings` 子类）设计为**可被参考实现继续子类化**——参考实现新增自己的业务配置分组（如 `FeedingSettings`）作为 `PlatformSettings` 子类的新字段，与平台字段共享同一份分层加载机制（环境变量 + `.env`），平台代码本身不包含任何业务字段。
3. **实现方式**：采用 `pydantic-settings`（与现状各仓库的 Pydantic Settings 风格一致），新增为 `adp` 的依赖。
4. **实现顺序**：`config` 先行 → SQL Adapter（依赖 `config.database.dsn`）→ `scheduling`（相对独立，可并行/最后做）。
